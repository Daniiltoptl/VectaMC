## Режим работы: длинный сеанс с проверяемыми результатами

После первого законченного этапа не заканчивай финальным ответом: узкие
проверки → осмысленный коммит → push своей ветки → следующий доступный этап.
Работай, пока есть ресурс сеанса и независимые задачи с проверенными основаниями.
Не останавливайся только потому, что очередная задача включает несколько пакетов,
несколько файлов или требует законченного сетевого пути.

До реализации каждой системы проверь код Vecta, соответствующие vanilla методы,
данные/генераторы и существующие тесты. Коротко зафиксируй, какое игровое действие
сейчас не работает и что станет работать. Не трать ночь на общий аудит всего
репозитория: очередь и общий VANILLA_PLAN уже существуют.

Отсутствующий метод/пакет, для которого есть эталон и понятная основа, — часть
реализации. Это отличается от отсутствующих данных, неясной архитектуры или
недостающего общего основания: при них выполняй CHECK-IN DISCIPLINE из AGENTS.
Не угадывай архитектуру, не делай заглушку и не коммить частичную общую основу.

Настоящий блокер запиши в `planning/night-02/blockers.md`: что проверено,
конкретный путь/метод, что отсутствует, риск расхождения и узкий вопрос владельцу.
Пока владелец спит, не считай молчание согласием. Можно продолжить только другую
действительно независимую задачу. Общая сломанная сборка или неверный эталон
не исчезают от смены ID. Повторные одинаковые сбои не лечи перебором команд.

Не запускай дополнительные агенты, Gemini/Mistral CLI или автоматизации.
Не устанавливай новые инструменты, не обновляй зависимости без необходимости,
не меняй AGENTS и не делай новый ренейм. Секреты не выводи.

### Первое действие после подготовки: N03 по настоящему сетевому пути

На момент передачи Codex проверил:

- `vecta-registry/src/data_components/components/books.rs` уже содержит
  Filterable, WritableBookContent и WrittenBookContent. Не создавай вторую модель.
- `vecta-protocol/src/packets/game/` ещё не содержит реализации edit-book и
  open-book. Их ID присутствуют в generated таблице; бери именованные generated
  константы, не вставляй числовые ID и не правь generated Rust.
- Java-пакеты существуют:
  `network/protocol/game/ServerboundEditBookPacket.java`,
  `network/protocol/game/ClientboundOpenBookPacket.java`.
- В `server/network/ServerGamePacketListenerImpl.java` есть `handleEditBook`,
  `updateBookContents`, `signBook`, `filterableFromOutgoing`.
- Поведение предметов: `world/item/WritableBookItem.java`, `WrittenBookItem.java`,
  `KnowledgeBookItem.java`; копирование — `world/item/crafting/BookCloningRecipe.java`.

Нужен путь codec → реальная регистрация/dispatch → обработчик игрока →
компоненты/инвентарь → сообщения клиенту, а не тест отдельно созданного компонента.
Прочитай Player/ServerPlayer.openItemGui и клиентский путь: не предполагай, что
редактируемая и подписанная книга открываются одинаковым серверным пакетом.

Особенно проверь следующие неочевидные контракты непосредственно в Java:

1. Допустимые слоты и выбор предмета проверяются по наличию нужного компонента,
   а не только по одному конкретному vanilla item ID. Не переноси ошибку мешков.
2. Packet string/list limits отличаются от общих сетевых лимитов компонентов;
   Java string length и число UTF-8 bytes нельзя подменить одним `str.len()`.
3. Подпись transmute-copy сохраняет нужные исходные components; затем убирается
   writable content и создаётся written content с правильными author/generation/
   resolved/filterable fields. Не конструируй голую книгу с потерей patch.
4. Проверь существующую text-filtering основу. Нет сервиса — не выдумывай
   результат фильтра и не добавляй блокирующий async wait в game tick. Если
   непонятен обязательный контракт, оформи точную зависимость по AGENTS.
5. В Java после text filtering стек читается заново из inventory в callback.
   Смена слота/предмета между запросом и применением не должна портить иной стек.
6. Для WrittenBook resolution и KnowledgeBook сначала проверь существующие
   command/text/recipe interfaces, не подменяй их фиктивным resolved=true
   или локальным списком рецептов. Статус по подзадачам должен быть честным.

Минимальные содержательные проверки N03: успешное сохранение, подпись,
main/offhand где применимо, неверный slot/component, предельные и превышающие
лимиты строки/страницы с Unicode, сохранность unrelated components,
повторная отправка после подписи, реальный handler/dispatch и save/load.
Добавляй только применимые регрессии, без тестов на очевидные константы.

## 6. Сборки на этой Windows-машине

Ночной сеанс до этого столкнулся с заполнением C: и зависаниями параллельной
сборки. Не повторяй это вслепую. Сначала проверь доступность и место на D:.
Если каталоги существуют и подходят, используй в текущем PowerShell:

```powershell
$env:CARGO_TARGET_DIR = 'D:\CodexBuilds\VectaMC'
$env:CARGO_INCREMENTAL = '0'
```

При необходимости выдели task-specific temp-каталог на D: и установи
`TMP`/`TEMP` только для сеанса, предварительно проверив путь/место.
Не меняй системные переменные навсегда. Не удаляй чужие build outputs,
исходники, `.vecta-cache/vanilla`, `minecraft-src` и пользовательские миры.
Не убивай все `rustc`/Java процессы по имени: часть может принадлежать другим
задачам. Проблему места или зависания фиксируй точным логом.

Узкие проверки для каждого игрового этапа:

```powershell
# Подставь фактический тестовый фильтр и затронутые crates.
cargo test --locked -p vecta-core --lib <test-filter> -j 1
cargo check --locked -p vecta-core -j 1
cargo fmt --all --check
```

После серии законченных задач и обязательно перед итоговой передачей:

```powershell
cargo check --locked --workspace -j 1
cargo test --locked --workspace -j 1
cargo clippy --locked --workspace --all-targets --all-features -j 1 -- -D warnings
cargo fmt --all --check
python -m unittest discover -s scripts -p "test_*.py" -v
python scripts/audit_vanilla.py
git diff --check
```

Сохраняй stdout/stderr сборок в ignored `.vecta-cache/`, а в журнал —
команды, exit code, длительность, итоги и точные диагностические сообщения.
Выполнение проверок не в полном составе объясни. Не выдавай Windows за Linux,
старый зелёный CI за проверку нового коммита или ignored за passed.
Если audit изменился, проверь причину и обнови соответствующие tracked reports;
не превращай число registrations в процент ванильности.

Если `typos`/`prek` уже настроены и требуются действующими правилами/CI,
выполни их без отключения проверок. Не трать ночь на установку новых
необязательных инструментов вместо реализации.

## 7. Контрольные точки, push и восстановление

- После каждого законченного этапа: узкие тесты → читаемый diff → запись

- Перед исчерпанием сеанса перестань начинать крупную новую систему,
  доведи текущий этап до проверяемого состояния и выполни финальные проверки.
- При незавершённом этапе не делай вид, что он готов. Сохрани точные пути
  незавершённой работы и её состояние отдельно от списка готовых задач.

  как законченную реализацию. Содержимое рабочей ветки должно быть понятно

1. Ветка, исходный и итоговый полные SHA, ссылка на GitHub compare,
   список коммитов и отдельный статус push. Если есть рабочие изменения —
   перечисли их, не скрывай грязное дерево.
2. Таблица N01–N20: `реализовано и проверено`, `проверено, уже работало`,
   `частично`, `блокер` или `не начато`, с соответствующими ID общего плана.
   «Частично» не означает выполненную родительскую задачу.
3. Для каждого результата: конкретный сценарий игрока до/после,
   точные vanilla классы/методы и относящиеся source/data paths Vecta.
4. Изменённые общие контракты, типы данных, codegen/extractor, сохранения
   и сетевые пути. Отдельно отметь риски для существующих потребителей.
5. Какие дефекты воспроизведены, чем закреплены регрессии; какие проверки
   выполнены фактически, результаты, ignored и известные ошибки окружения.
6. Настоящий клиент, 2+ игрока, Mojang comparison, unload/restart:
   выполнено/не выполнено и чем подтверждено. Не подменяй одно другим.
7. Оставшиеся игровые ограничения, проверенные блокеры с точными вопросами,
   что не вошло в реализацию и какую задачу безопасно брать следующей.

Codex будет читать исходники и проверять поведение, а не принимать число
тестов за доказательство. Оставь серию небольших понятных изменений,
которые можно проверить и при необходимости исправить по отдельности.

## Уточнения к журналу и финальной передаче

Создай `planning/night-02/progress.md`, `blockers.md`, `scenarios.md` и
`report.md`, когда соответствующее содержимое действительно появляется.

игровой базе, симптомах регрессии или требовании действующих правил, а не
для расходования первой части ночи. После правок запускай узкие проверки;
полный suite и Clippy обязательны перед итоговой передачей новых изменений.

Выполненные `cargo fmt`/`audit` иногда меняют чужие файлы. Просматривай diff
и явно stage только свои логические изменения, без чужого report.md.

Не используй существующее чужое форматирование как причину не проверять свой diff.

Если готов первый этап и его проверки зелёные, коммить и push в свою ветку,

безопасный следующий шаг. **Не пиши «full vanilla готово» по числу тестов.**
