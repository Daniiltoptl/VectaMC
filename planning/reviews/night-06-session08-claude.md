## Найденные расхождения и исправления

### 1. `floor_div` и `floor_mod` считались по Евклиду

`checked_div_euclid` и `rem_euclid` совпадают с `Math.floorDivExact` и
`Math.floorMod` только при положительном делителе. При отрицательном результат
другой: `floorDiv(7, -2) = -4` (было `-3`), `floorMod(7, -2) = -1` (было `1`).
Тесты покрывали только делитель `2`. Переписано, добавлена таблица с
отрицательным делителем.

### 2. `Difference` не падал при переполнении

Java использует `Math.subtractExact`, значит переполнение даёт ошибку и итог `0`.
В Vecta стоял `wrapping_sub`. Исправлено на `checked_sub`.

### 3. NaN терялся в `max`, `min` и `pow`

`f32::max`/`min` игнорируют NaN, а `Math.max`/`min` его сохраняют. `powf` следует
C: `pow(1, NaN) = 1`, в Java это NaN. Добавлены `java_max`, `java_min`, `java_pow`.

### 4. Таймеры горения печи писались как short

Отчёт заявлял перевод таймеров на int, но `lit_time_remaining` и `lit_total_time`
по-прежнему сохранялись и читались как short. Java использует `putInt` и
`getIntOr`, поэтому мир с ванильным форматом терял время горения при загрузке, а
значения больше 32767 обрезались. Исправлено, добавлен round-trip тест на 40000.

### 5. Лишняя точность в расчёте времени готовки

Java считает `int / float` и `float * int` во float, Vecta считала в double.
При таймере 5 из 200 Java даёт 5, а прежний код 6. Переведено на f32, добавлен
тест. Также убран фильтр `is_finite` при загрузке `speed_multiplier`: в Java его
нет.

### 6. `/data compute` держал блокировку RNG во время записи

`with_level` — обычная нереентерабельная блокировка, а `apply_source` работал
внутри неё. Запись может запускать обновления блоков; чтение компаратором сундука
с лут-таблицей дошло бы до того же потока RNG и повесило бы сервер. Такой случай
отдельно не воспроизводился: исправление устраняет саму возможность. Теперь
внутри блокировки только вычисление, запись идёт после неё.

## Проверено и совпадает с 26.3

- Protocol id `context_float_provider` = 55 и `context_int_provider` = 56:
  сверены с полным порядком регистрации `ArgumentTypeInfos`.
- Дерево `compute`, параметры `LootContextSources`, порядок «контекст → провайдер
  → `manipulateData`», `getFloat`/`getInt` вместо `OrThrow`.
- `serverTick` печи: порядок таймеров, `consumeFuel`, охлаждение, `canPlaceItem`,
  сброс при смене входа.
- Провайдеры `Average`, `Binomial`, `FromFloat`, `Power` (int), `Quotient`,
  `Modulus`, `Sum`, `Product`, `Truncate`, `Length`, `Modulus` (float).

## Не исправлено, передано исполнителю

- Контекст печи: Java передаёт `BLOCK_STATE`, `BLOCK_ENTITY`, `ORIGIN`,
  `CONTAINER`, Vecta только первые и `ORIGIN` — два параметра, а не три, как
  писал отчёт. Сейчас configured values их не читают.
- `CookingFuel` хранит `Identifier`, а Java — `ResolvableInt`/`ResolvableFloat`,
  где возможна и inline-форма. Предмет с inline-топливом сейчас не поддержан.
- `block_entity_loot_ref` в `compute` заполняет только тип, без имени и инвентаря.
- Открытые формы B-06-11 и `slot_source`.
- Воронка не видит `WorldlyContainerHolder`: это понадобится компостеру.
