## Находки и исправления

### P1 — seeded RNG не делал порядок вычисления лута ванильным

В `LootTable.get_random_items` функции таблицы применялись после всех pools,
а в `LootPool.add_random_items` — после всех rolls. Java использует decorated
consumers: entry → pool modifier → table modifier → output, для каждого stack
до следующего броска. Nested table также передаёт stacks в этот же consumer.
Случайная функция меняла последующий выбор entry при том же seed.

Пример из Java Random(42): чередование `nextInt(2)` и `nextInt(20)+1` даёт
`[(1,4),(1,5),(0,6)]`; прежний код давал `[(1,5),(0,11),(1,6)]`.
Nested item/count functions давали `[20,9]` вместо `[15,14]`.
Эти ошибки существовали до последнего сеанса; перевод RNG их не устранил.

Исправление: потоковая выдача с context-aware consumers. Nested tables используют
raw emission; деление по stack limit выполняется на внешней границе после modifiers.
Нет второго RNG, отложенного batch post-processing или новых placeholders.

### P1 — RandomSequences имели неправильного владельца и откатывались при рестарте

В 26.3 `MinecraftServer` хранит `RandomSequences`; `getRandomSequence` берёт
seed из server world-gen settings. Прежний `LevelRandom` создавал отдельную
непостоянную карту на каждом World, поэтому одинаковый ключ в разных измерениях
начинался заново; reload также возвращал поток к исходному seed.

Владелец попросил поведение как в vanilla. В локально подготовленном коде один owner на Vecta `Server`,
с seed его default world; все загруженные worlds, включая разные Vecta domains,
используют этот общий набор. Legacy `Level.random` остаётся отдельным для мира.
Связывание выполняется до gameplay в обоих server constructors. World хранит
ссылку на данные потока, не ссылку на Server.

Сохраняются два signed seed words каждого Xoroshiro-потока и defaults:
`salt`, `include_world_seed`, `include_sequence_id`. Gaussian cache не входит
в vanilla codec и не добавляется в persistent state. Запись получает snapshot;
последующий draw остаётся dirty, ошибка I/O не подтверждает сохранение.
Используются существующие async autosave/shutdown paths, без disk waits в tick.

Формат хранения Vecta сохранён: **`data/random_sequences.toml`** у server default
world через `SavedDataManager`, как другие typed saved data проекта. Это не
import/export Mojang `random_sequences.dat` и не заявление о двоичной совместимости
с официальным форматом мира. Игровое продолжение потока проверяется отдельно.

**Дополнительная архитектурная зависимость:** `WorldTickWorkers.tick_all` сейчас
сначала отправляет запрос всем workers, затем ждёт ответы. Java
`MinecraftServer.tickChildren` тикает levels последовательно. Поэтому общие
потоки защищены от потери состояния, но распределение draw между параллельными
мирами зависит от scheduling. Это не закрытая vanilla-совместимость порядка.
Владельцу задан отдельный вопрос о последовательном dispatch игровых world ticks;
генерация и I/O не требуют такого ограничения. До решения порядок workers не меняется.
Подготовленные server-wide RNG changes остаются локальными до решения и не
выдаются за завершённую общую foundation. Сохранность и sharing как структура
данных проверены; порядок обращений из параллельного игрового цикла — отдельный gate.

### P2 — отсутствовал внешний stack splitter и слишком рано отбрасывались нулевые stacks

Java `LootTable.createStackSplitter` нормализует размер после modifiers:
129 stone превращаются в 64/64/1. Прежний код возвращал один stack 129.
Кроме того, entry с count 0 исчезал до outer modifier, хотя тот мог снова
установить count 5. Теперь все modifiers получают stack, затем применяется splitter.

Старый тест лимита looting у stray теперь отбирает непустые drops: Java
`getRandomItems` может вернуть пустой stack. Проверка лимита непустого дропа
сохранена, ожидаемое количество не ослаблено до произвольного диапазона.

### P2 — UniformBonusCount при level 0 пропускал вызов RNG

Java `ApplyBonusCount.UniformBonusCount.calculateNewCount` всегда вызывает
`nextInt(bonusMultiplier * level + 1)`. Даже `nextInt(1)` продвигает поток.
Условие `level > 0` убрано. Regression сравнивает следующий int с Java Random(42):
после `nextInt(1)` он равен 234785527, а не -1170105035.

### P2 — возврат снежка при rejected entity insertion расходился с Java

Factory возвращала None, а behavior возвращал весь stack без расхода и level events.
В `Projectile.spawnProjectile` Java игнорирует boolean `addFreshEntity`, выполняет
spawn hooks; `ProjectileDispenseBehavior.execute` затем расходует один предмет.
Теперь Vecta также сохраняет порядок hooks, consumption и sound/smoke events,
записывая причину отказа в log. Regression использует настоящую unloaded-chunk
ошибку world insertion; source dispenser остаётся в загруженном chunk.

### Неактуальные блокеры: living capability и наблюдение game events

`Entity::as_living_entity()` уже был в переданном HEAD и использовался во многих
consumers, включая players. Новый `as_living()` не нужен. Метод выбора equipment
slot перенесён с Mob на его фактического владельца LivingEntity; общая установка
слота вызывает equip hook после освобождения inventory lock.

Подключён component-based `EquipmentDispenseItemBehavior`: сначала явная registry
запись предмета, затем equippable fallback. Проверяются living predicate, target AABB,
свободный/доступный slot и dispensable. Mob получает guaranteed drop и persistence.
Fallback выбрасывает item; dropper продолжает обходить equipment dispatch.

`on_equip_item` теперь также отправляет EQUIP/UNEQUIP. Silent подавляет sound,
но не game event; player отправляет эти events только для humanoid armor slots.
Событие может reenter inventory через listener: mutex в этот момент освобождён.

World game events уже наблюдаемы через `GameEventListener`, как в старых jukebox
tests. Добавлены реальные listener regressions для пустого dispenser BLOCK_ACTIVATE
и equip/unequip. Отдельный mock event bus или изменение game-event foundations не нужны.
