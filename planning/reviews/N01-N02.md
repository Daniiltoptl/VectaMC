# Ревью ночного сеанса 01: инвентарь и мешки

База ночного сеанса: `180ee147ed50cac0f13ad2dd53d045e0efa54466`.
Реализация: `ca764fa5d`, `ac6d04fb5`, `bfbdd45e1`.
База ревью: `4be347ab3a091db6462bf47fe20bcfaf4360c1e5` (включает последние
документы ночного сеанса; игровые изменения после `bfbdd45e1` отсутствуют).

Версия Cargo и `minecraft-src/.vecta-reference.json` совпадают: **26.3**,
5037 Java-исходников. Эталон не пересоздавался, generated Rust и извлечённые
данные вручную не редактировались.

## Что действительно сделано за ночь

Добавлены основные действия мешка и пакет выбора, а также обработка
`QUICK_MOVE` с внешним слотом `-999`. Последняя правка соответствует
`AbstractContainerMenu.doClick`: внешний слот обрабатывается до разделения
`PICKUP` и `QUICK_MOVE`.

Ветка не реализует всю ночную очередь. N01 остался частичным, N03–N20
не начаты. Отчёт N02 был шире фактической реализации и тестирования:
уничтожение мешка и существенные края взаимодействий не проверялись.

## Исправленные расхождения

### 1. Отказ первого обработчика не вызывал второй

`MenuBehavior::try_item_click_behavior_override` выбирал между предметом
на курсоре и в слоте по признаку «курсор является мешком». Если первый
обработчик возвращал false, второй не запускался. В частности, при правом
клике одного мешка по другому не сбрасывался выбор содержимого второго.

Теперь соблюдается последовательность `AbstractContainerMenu`:
первый обработчик → при отказе второй → при отказе обычный pickup.
Вместо доступа к конкретному `BundleItem` общий код использует capability
`ItemClickBehavior`. Обычные предметы не получают лишний вызов записи слота.

### 2. Выбор был ошибочно привязан к классу предмета

`AbstractContainerMenu.setSelectedBundleItemIndex` вызывает
`BundleItem.toggleSelectedItem` для содержимого указанного слота без проверки
класса Item. Решение зависит от наличия `BUNDLE_CONTENTS`.

Убрана проверка `as_bundle`: компонент на другом предмете также получает
выбор. Предмет без компонента, неверный слот и повторный выбор обработаны
по исходнику. Добавлена проверка через player packet handler.

### 3. Использование из руки вызывало неправильный drop path

Было `spawn_dropped_item(removed, true, false)`: случайное направление,
нет thrower, нет обычного swing/drop statistics. Vanilla вызывает
`player.drop(stack, true, Prediction.PREDICTED)`.

Используется имеющийся `Player::drop_item` с `Prediction::Predicted`:
направленный бросок, thrower, pickup delay и статистика. Содержимое тратится
и в creative, как у vanilla bundle use. Тест охватывает обе руки и оба режима.
Позиция звука сброса исправлена на центр блока игрока, как у
`Level.playSound(..., entity.blockPosition(), ...)`.

### 4. Уничтожение предмета удаляло всё содержимое

В `ItemEntity.hurt` существовал TODO вместо `ItemStack.onDestroyed`.
Добавлен действующий item hook с реализацией для мешков. Перед удалением
мешка его компонент очищается, а копии содержимого появляются на его позиции
обычными item entities, без thrower и player-drop delay. Путь соответствует
`BundleItem.onDestroyed` и `ItemUtils.onContainerDestroyed`.

Причина удаления item entity при разрушении исправлена на `Discarded`,
соответствующую `ItemEntity.hurtServer`. Естественный despawn этот hook
не вызывает. Поведение других container items этим пунктом не объявляется
завершённым: их конкретные overrides относятся к собственным задачам.

### 5. Derived Default выбирал индекс 0 вместо отсутствия выбора

Новые структуры имели `#[derive(Default)]`, который инициализировал индекс
нулём. После вставки предметов первый запрос выбора индекса 0 отменял его.
Default теперь использует `empty()`/`new()`; добавлена проверка реальной
последовательности вставки и выбора.

### 6. Арифметика принимала действие, на котором vanilla выдаёт ошибку

Вычисление оставшейся вместимости расширяло произведения до i64 и скрывало
переполнение Commons Lang Fraction. Оно могло принять новый предмет, после
чего следующее `as_mutable()` очищало содержимое из-за ошибочного веса.
Mutable также пересчитывал вес вместо сохранения результата vanilla-операций.

Для проверки извлечён только `commons-lang3-3.20.0.jar` из имеющегося
официального `server-bundled.jar`. Изолированный Java-тест не запускает
Minecraft и не принимает EULA. Для последовательно вставленных предметов
с разными пользовательскими `max_stack_size` получены:

| Размер stack | Максимальное число новых предметов | Вес после одного |
| --- | --- | --- |
| 97 | 97 | 1/97 |
| 89 | 88 | 186/8633 |
| 83 | 81 | 24071/716539 |
| 79 | 76 | 2618148/56606581 |
| 73 | `ArithmeticException: overflow: mul` | операция не завершена |

Это входы теста, а не вручную выписанные vanilla registry values.
По указанию владельца сохранён ванильный путь ошибки. Добавлены checked
сложение/вычитание и деление с сокращением дробей и i32-переполнением,
running weight и `Result` на границах операций. Клик с ошибкой не считается
успешным и не доходит до применения клиентских prediction hashes.

Проверена полная цепочка 26.3: `AbstractContainerMenu.clicked` оборачивает
исключение; `PacketProcessor.ListenerAndPacket` передаёт его в
`ServerPacketListener.onPacketError`, который пишет ошибку в лог и подавляет
её. Vecta также логирует ошибку и продолжает обработку следующих пакетов.
Это не отключение линтера, не скрытый fallback в арифметике и не специальный
«успешный отказ» без диагностики.

Ошибка во время использования предмета относится к entity tick, где vanilla
`Level.guardEntityTick` превращает её в fatal tick error; она не подменяется
пакетным обработчиком. Некорректное runtime-содержимое закреплено отдельным
тестом ожидаемой ошибки тика.

### 7. Конвертация молча пропускала неперсистентные предметы

`to_immutable` использовал `filter_map` и выбрасывал элементы, не прошедшие
проверку persistent codec. Vanilla `ItemStackTemplate.fromNonEmptyStack`
создаёт runtime snapshot без такой codec-проверки.

Добавлен crate-private runtime snapshot constructor на существующей основе
stream template. Он сохраняет item/count/components; persistent validation
остаётся на границе сохранения. Конвертация возвращает ошибку вместо
пропускания элементов. Тест отдельно проверяет сохранность runtime-компонента,
который persistent codec не принимает.
