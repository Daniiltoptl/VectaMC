# Ревью V05.09a: рамки

Проверяется ветка `codex/gemini-v05-09a`, исходный коммит `b22e55102`
поверх `a2db838b6`. Эталон: официальные исходники Minecraft Java 26.3,
полученные проектным скриптом; provenance — `minecraft-src/.vecta-reference.json`.

## Найденные расхождения

1. **P1 · ENTITY_DATA при установке.** `ItemFrameItem.use_on` вызывает только
   `apply_implicit_item_stack_components`. В `HangingEntityItem.useOn` вызывается
   `EntityType.createDefaultStackConfig`, который также применяет typed entity
   data. Поэтому `Fixed`, `Invisible`, содержимое и направление из компонента
   теряются. Общая реализация `apply_item_stack_components` уже есть в проекте;
   нужно использовать её до `survives`, включая существующие проверки типа
   и прав, без дублирования загрузчика NBT.
2. **P2 · Имя выпавшей рамки.** `drop_frame_and_contents` создаёт обычный stack
   рамки. В `ItemFrame.getFrameItemStackWithData` копируется `CUSTOM_NAME`
   сущности. Ошибка затрагивает обычную и светящуюся рамки.
3. **P2 · Знак поворота.** `rem_euclid(8)` превращает NBT-поворот `-1` в `7`.
   В `ItemFrame.setRotation` используется Java `%`: результат `-1`, а выход
   компаратора при наличии предмета — `0`, а не `8`.
4. **P2 · Повторная загрузка без полей.** Если `ItemRotation` или
   `ItemDropChance` отсутствуют, код сохраняет старое значение. Vanilla
   `readAdditionalSaveData` каждый раз устанавливает defaults `0` и `1.0`.
5. **P2 · Legacy Facing и числовые NBT.** `Direction.LEGACY_ID_CODEC`
   сначала читает `Codec.BYTE`, затем использует `abs(id % 6)`. Код Gemini
   принимает только обычные значения 0–5 и частично типы NBT. Для остальных
   полей `TagValueInput` тоже преобразует числовые теги; float/double byte
   преобразуются через floor, в отличие от Number.byteValue в Codec.BYTE.
   Например, ItemRotation=-1.2d даёт -2; Facing=257 даёт UP.
6. **P2 · Граница мира.** Проверка обеих крайних точек на нахождение внутри
   border отличается от `HangingEntity.hasLevelCollision`: ванилла проверяет
   пересечение collision shape и учитывает положение сущности относительно
   границы. Касание без пересечения разрешено; дальняя внешняя граница не
   должна искусственно становиться коллизией рядом с рамкой.
   Collision shape округляется наружу через floor/ceil границ до целых блоков;
   это учтено в регрессионном сценарии, а не заменено проверкой raw bounds.

## Что дополнительно проверяется

- Установка и вставка предмета: все шесть граней × две руки × два варианта
  рамки × survival/creative.
- Пересечение рамок с одним направлением, включая обычную и светящуюся.
- Потеря опоры и периодическая проверка на 101-м тике, как у
  `BlockAttachedEntity.tick` с post-increment.
- Существующие тесты рамок, компараторов, attached entities и spawn components.
- Тестовые рамки получают уникальные runtime ID: добавленная в мир рамка
  не конфликтует с ID выпадающего предмета при параллельном прогоне.

В исходном наборе 17 тестов нет переключения game mode на creative;
соответствующая фраза в отчёте и CHANGELOG была шире фактической проверки.
Тест glow-варианта только вызывает звук и не проверяет полученный sound packet.
Результаты unit-тестов не следует выдавать за проверку звука настоящим клиентом.

## Границы этапа

Map saved data, удаление frame marker и лимит tracked maps остаются открытой
задачей V05.07. Entity pick-block и остальные типы V05.09 не реализованы.
Путь `ItemFrame.getSlot(0)` для командного доступа к содержимому также требует
общего SlotAccess и соответствующих команд V12; его нет в этой реализации.
Пока это ограниченный этап рамок, а не полное соответствие всех их сценариев.
Настоящий клиент, два игрока и EULA в ходе ревью не использовались.
